The problem

Why this needed to exist

Most organisations don't have a knowledge problem, they have a finding problem. The answer is in a contract, a deck or a policy PDF somewhere on a shared drive, and keyword search can't find it unless you already know the exact wording.

Ledger is the retrieval layer underneath Cite: the part that decides which passages the model gets to read.

Ledger is in development. This page describes the product definition and planned architecture. There is no public demo yet.

The product

How it works

  1. Ingest documents from folders and split them into passages that keep their headings and page numbers.
  2. Embed each passage and store it in a vector index (pgvector) alongside its metadata.
  3. For each question, retrieve the most relevant passages, re-rank them and pass only those to the model.
  4. Return the answer with the section and page it came from, using the same citation approach as Cite.
Product decisions

The calls that mattered

Define "good retrieval" before building

The first artefact is an evaluation set of real questions and the passages that should answer them. Without it, there's no way to tell whether a change helped.

Keep structure, not just text

Headings, clause numbers and page numbers are kept with every passage, because that's what a reviewer needs to verify an answer.

Orchestrate with a graph

LangGraph makes the retrieve, re-rank, answer and check steps explicit, so each one can be tested and improved separately.

Measuring success

What I'd measure

This is a prototype, so these are the metrics I'd use to judge it in production, not results I'm claiming.

Recall@5Share of questions where the right passage is in the top five results
Answer groundednessShare of answer sentences supported by a retrieved passage
LatencyTime from question to answer at the 95th percentile
FreshnessTime from a document changing to it being searchable
